# 灰度发布与回滚演练清单（P4）

## 1. 发布前检查
- 确认镜像已构建通过：`docker compose build backend`
- 确认数据库迁移可执行：`flyway_schema_history` 无失败记录
- 确认健康检查可用：`GET /actuator/health`
- 确认关键指标可读：`GET /actuator/metrics`
- 确认故障注入开关默认关闭：`game.chaos.enabled=false`

## 2. 灰度发布步骤（单机 Docker Compose）
1. 构建新镜像并打版本标签（建议）
   - `docker build -t doomsday-backend:canary -f backend/Dockerfile backend`
2. 启动灰度实例（建议新端口）
   - 可复制 `backend` 服务为 `backend-canary`，映射 `8081:8080`
3. 验证灰度实例
   - `GET http://localhost:8081/actuator/health`
   - 执行一轮建局与提交回合冒烟
4. 小流量切换
   - 通过网关或测试客户端将 5%-10% 流量导向 `8081`
5. 观察指标
   - 成功率、P95、错误码分布（重点关注 `INTERNAL_ERROR`、`AGENT_ABORT`）

## 3. 回滚触发条件（建议）
- 5 分钟窗口内错误率 > 3%
- P95 延迟较基线上升 > 30%
- 出现连续状态冲突或严重业务错误（会话推进异常）

## 4. 回滚流程
1. 停止流量导向灰度实例
2. 下线灰度容器：`docker compose stop backend-canary`
3. 恢复稳定版本容器（或重启主服务）
4. 验证健康与核心链路
   - 建局 -> 提交回合 -> 选项提交
5. 记录回滚事件
   - 时间、触发条件、错误码、traceId 样本

## 5. 故障注入演练流程
1. 演练环境启用：`game.chaos.enabled=true`
2. 使用请求头触发 failpoint：`X-Doomsday-Failpoint`
3. 推荐演练点
   - `submitTurn.beforeOrchestrator`
   - `submitTurn.afterOrchestrator`
   - `chooseOption.beforeApply`
   - `comeback.beforeApply`
4. 记录对比数据
   - 正常流 vs failpoint 的成功率、平均耗时、P95
   - 可使用脚本：`scripts/p4/load_compare.ps1`

## 6. 演练后恢复
- 关闭故障注入：`game.chaos.enabled=false`
- 重新跑一轮正常流冒烟
- 归档演练报告（指标截图 + 关键 traceId）
